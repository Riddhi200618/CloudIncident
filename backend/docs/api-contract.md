This document describes the deployed CloudIncident backend and its API Gateway integration. All five API endpoints have passed initial live HTTP tests. CORS has been configured, but integration with the React frontend is still pending.

## 1. Common conventions

- Send `Content-Type: application/json` for POST and PATCH requests.
- All Lambda responses use an API Gateway proxy response with `statusCode`, `headers`, and a JSON-serialized `body`. Through API Gateway proxy integration, clients receive the parsed HTTP response body:

```json
{
  "success": true,
  "message": "Human-readable message",
  "data": {}
}
```

- For errors, `success` is `false`, `data` is `null`, and `message` explains the failure.
- Incident IDs are server-generated strings like `INC-1826b05a-0a59-437a-95b6-dcfbf991fd85` (UUID-based), **not** sequential numeric IDs.
- Dates/times are UTC ISO 8601 strings generated by the backend.
- There is **no documented authentication or authorization enforcement** in the current Lambda handlers; `reportedBy` is client-supplied. Do not assume the API is secured for public production use.

## 2. Incident object

Example shape (values are illustrative, not a live response):

```json
{
  "incidentId": "INC-1826b05a-0a59-437a-95b6-dcfbf991fd85",
  "title": "Projector not working",
  "description": "Projector is not displaying output",
  "category": "IT Equipment",
  "location": "Lab 204",
  "priority": "High",
  "reportedBy": "student001",
  "assignedTo": "",
  "status": "Open",
  "createdAt": "2026-10-27T12:00:00+00:00",
  "updatedAt": "2026-10-27T12:00:00+00:00",
  "resolutionRemarks": "",
  "timeline": [
    {
      "status": "Open",
      "timestamp": "2026-10-27T12:00:00+00:00",
      "remarks": "Incident reported"
    }
  ]
}
```

`priority` is one of `Low`, `Medium`, `High`, `Critical`. `status` is one of `Open`, `Assigned`, `In Progress`, `Resolved`, `Closed`. `assignedTo` is the backend field name, **not** `assignee`. Timeline entries use `remarks`, **not** `note`, and the current backend does not store `actor`.

## 3. POST /incidents — Create incident

### Request

All six fields are **required, nonempty strings**. `priority` must exactly match an allowed value. The Lambda does not currently enforce a fixed category list.

```json
{
  "title": "WiFi not working",
  "description": "WiFi is unavailable in Lab 301",
  "category": "Network",
  "location": "Lab 301",
  "priority": "High",
  "reportedBy": "student002"
}
```

### Success — HTTP 201

The incident ID and timestamps below are illustrative examples, not fixed values. The backend generates fresh values for each incident.

```json
{
  "success": true,
  "message": "Incident created successfully",
  "data": {
    "incidentId": "INC-1826b05a-0a59-437a-95b6-dcfbf991fd85",
    "title": "WiFi not working",
    "description": "WiFi is unavailable in Lab 301",
    "category": "Network",
    "location": "Lab 301",
    "priority": "High",
    "reportedBy": "student002",
    "assignedTo": "",
    "status": "Open",
    "createdAt": "2026-10-27T12:00:00+00:00",
    "updatedAt": "2026-10-27T12:00:00+00:00",
    "resolutionRemarks": "",
    "timeline": [{"status": "Open", "timestamp": "2026-10-27T12:00:00+00:00", "remarks": "Incident reported"}]
  }
}
```

The backend generates `incidentId`, status `Open`, timestamps, empty assignment and remarks, and initial timeline entry. The **updated CreateIncident Lambda returns the full created incident**.

### Errors

- `400` — `Missing or invalid field: <field>`, `Invalid priority value`, or `Invalid request body` / `Invalid JSON body`.
- `500` — database or internal error.

## 6. PATCH /incidents/{id} — Update incident

### Request

Allowed keys **only**: `status`, `assignedTo`, `resolutionRemarks`. At least one allowed key must be provided. Do **not** send `assignee`, `updatedBy`, `actor`, or any other key; the current Lambda rejects unknown keys with `400`.

Example assignment:

```json
{
  "status": "Assigned",
  "assignedTo": "IT Department"
}
```

Example progress update:

```json
{"status": "In Progress"}
```

Example resolution:

```json
{
  "status": "Resolved",
  "resolutionRemarks": "Replaced faulty HDMI cable and verified display"
}
```

Example closure:

```json
{"status": "Closed"}
```

### Status transition rules

`Open` → `Assigned` → `In Progress` → `Resolved` → `Closed`

- Only **same-status** or **one-step-forward** transitions are allowed.
- Skipping a stage or moving backward returns `400` (`Invalid status transition`).
- An incident must have a nonempty `assignedTo` before entering `Assigned` or any later status.
- `Resolved` and `Closed` require nonempty `resolutionRemarks` (previously saved remarks count).
- Updating only assignment or remarks while keeping the same status is permitted, subject to validation.
- Status changes append a timeline entry with `status`, `timestamp`, and `remarks`. Assignment-only or remarks-only updates **do not** append a timeline entry in the current Lambda.
- The current Lambda does **not** accept `updatedBy` or record a timeline `actor`.

### Success — HTTP 200

```json
{
  "success": true,
  "message": "Incident updated successfully",
  "data": {"incidentId": "INC-1826b05a-0a59-437a-95b6-dcfbf991fd85", "status": "Assigned", "assignedTo": "IT Department"}
}
```

`data` is the **full updated incident record** (abbreviated above).

### Errors

- `400` — missing ID, invalid JSON/body/fields/status/transition/assignee/remarks, or missing required assignment/remarks.
- `404` — incident not found.
- `500` — database or internal error.

**Implementation note:** The current handler uses read-then-`put_item` without conditional concurrency control. Avoid concurrent edits to the same incident during the initial demo; a future hardening task should add optimistic locking or conditional writes.

## 7. GET /stats — Dashboard statistics

### Request

No request body. Counts are computed from all DynamoDB incident records.

### Success — HTTP 200

```json
{
  "success": true,
  "message": "Dashboard statistics retrieved successfully",
  "data": {
    "total": 2,
    "open": 1,
    "assigned": 0,
    "inProgress": 0,
    "resolved": 0,
    "closed": 1,
    "critical": 0,
    "byStatus": {"Open": 1, "Assigned": 0, "In Progress": 0, "Resolved": 0, "Closed": 1},
    "byPriority": {"Low": 0, "Medium": 0, "High": 2, "Critical": 0},
    "byCategory": {"Network": 1, "IT Equipment": 1},
    "priorityCounts": {"Low": 0, "Medium": 0, "High": 2, "Critical": 0},
    "categoryCounts": {"Network": 1, "IT Equipment": 1}
  }
}
```

**Illustrative counts only.** This matches the **updated GetStats Lambda deployed by the backend developer**. `resolved` counts **only** `Resolved`, while Riddhi's current mock implementation counts both `Resolved` and `Closed` under `resolved`; the frontend should decide whether to display `resolved + closed` as a combined count.

### Errors

- `500` — database or internal error.

## 8. Frontend integration checklist (Riddhi)

The existing React app's `frontend/src/services/incidentService.js` can adapt backend responses without changing the DynamoDB schema or the Lambda field names.

1. For **all five endpoints**, parse the `{success, message, data}` response and return `data` to the components. On `success: false`, show the backend error message.
2. Convert incident objects: `incidentId` → `id`; `assignedTo` → `assignee` (use `Unassigned` for display only when blank); each timeline `remarks` → `note`. The backend currently has no timeline `actor`, so provide a UI fallback such as `System` rather than assuming the backend supplied one.
3. For PATCH, convert `assignee` → `assignedTo`; omit `updatedBy` and other unsupported keys. Ensure the admin UI permits only the allowed next status, and sends required assignment/resolution remarks.
4. For POST, send the six documented fields; normalize the returned full incident object before using it in React.
5. For GET `/stats`, use the updated `data` structure; if a dashboard card groups Resolved + Closed, compute `data.resolved + data.closed` in the frontend. Category and priority breakdowns are available in `categoryCounts` and `priorityCounts`.
6. Use the deployed API Gateway base URL, set the actual base URL, switch off mock mode, and confirm CORS preflight for `POST` and `PATCH` as well as `GET`. Do not put AWS credentials in Vite environment variables.
7. Test an incident end to end: create → list → details → assign → in progress → resolve → close → dashboard updates.
